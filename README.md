# Humanizer-zh：中文文本润色 Skill

编辑已有文章、评论和文档中的空话、重复及模板化表达，保留事实、确定程度和作者声音。输入是一段文字或一个文件，默认输出最终改写稿；没有问题的句子可以不改。用户要求时也检查标题（含图注、表题），按 H.md 的检查清单给出建议。

这是一份由 Agent 读取执行的编辑指导，本身不做文本检测。它不能证明文章由谁撰写，也不保证通过任何 AI 检测器。

本项目基于 ds flash 4.1 模型进行了一些调整和测试；据此修订的措辞与新增的测试文本见 [CHANGELOG.md](CHANGELOG.md)。

本仓库是 [op7418/Humanizer-zh](https://github.com/op7418/Humanizer-zh) 的 fork，沿用上游的正文结构、示例和 MIT 许可；相对上游的改动见 [CHANGELOG.md](CHANGELOG.md)。

## 安装

### 方法一：通过 npx 一键安装（推荐）

```bash
npx skills add https://github.com/shikakokou/Humanizer-zh.git
```

命令会把技能安装到 skills 目录，不需要手动复制文件。

### 方法二：通过 Git 克隆

```bash
# 克隆到所用 Agent 的 skills 目录（下面以 Claude Code 为例，其他 Agent 换成对应目录）
git clone https://github.com/shikakokou/Humanizer-zh.git ~/.claude/skills/humanizer-zh
```

### 方法三：手动安装

1. 下载本项目的 ZIP 文件或克隆到本地
2. 将 `Humanizer-zh` 文件夹复制到所用 Agent 的 skills 目录。Claude Code 的默认位置：
   - **macOS/Linux**: `~/.claude/skills/`
   - **Windows**: `%USERPROFILE%\.claude\skills\`

   DSH 的 skills 目录为 `~/.dsh/skills/`（Windows 为 `%USERPROFILE%\.dsh\skills\`）。
3. 确保文件夹结构如下：

   ```
   <skills 目录>/humanizer-zh/
   ├── SKILL.md              # 流程与约束
   ├── reference/
   │   ├── patterns.md       # 模式目录（分组与条目）
   │   ├── A.md … G.md       # 正文检查点详解与示例
   │   ├── H.md              # 标题检查
   │   ├── I.md              # AI-ish 表达
   │   ├── J.md              # 段落问题
   │   └── optional.md       # 过度截短、省略与口语化（可选）
   ├── README.md
   ├── scripts/
   │   ├── apply-edits.mjs            # 按补丁落盘
   │   ├── apply-edits.test.mjs       # node:test 单测
   │   ├── number-paragraphs.mjs      # 生成编号副本（段号预编号）
   │   └── number-paragraphs.test.mjs # node:test 单测
   └── tests/                # 案例与只读结构检查脚本（可选）
   ```

### 验证安装

重启 Agent 或重新加载 skills 后，在对话中调用该技能；Claude Code 输入：

```
/humanizer-zh
```

安装成功后，该技能即可使用。

## 使用

粘贴文本：

```text
请用 humanizer-zh 润色下面的文章，保留技术评论的语气：
[原文]
```

编辑文件：

```text
请用 humanizer-zh 润色 article.md 中的正文，并直接改文件。
```

逐条审阅（要求逐条对照）：

```text
请用 humanizer-zh 逐条审阅这篇说明，给出每一条的判定和改写建议，不要直接改文件。
```

检查标题（只检查，不改正文）：

```text
请用 humanizer-zh 检查这篇文档的标题和分节标题，给出建议，不要改正文。
```

只审阅时说明“给出建议，不修改文件”。有作者样本时可一并提供，Skill 会借鉴表达习惯，但不会把样本中的经历、数据或观点写入原文。改标题前要说明是否允许动锚点：标题是链接目标时，改动会破坏目录和交叉引用。

## 工作流程

四件事，顺序不能换：列命中、合并去重、按命中改、复核。先用 `node scripts/number-paragraphs.mjs` 把待编辑文本生成编号副本：段号 `[N]` 印在每段开头（标题、列表项、表格行各算一段，引用块和代码块整体各算一段），纯脚本、不耗模型调用，副本除前缀外与原文件逐行相同；扫描子 agent 读副本、直接引用段号，不自己数段、不在思考里枚举全文。扫描把正文分成四份派独立子 agent（A＋E＋D＋F、B＋G、C＋I、J＋H；用户同意处理过度截短时另加 O 一份，只给 `optional.md`。分组文件开头就是该组的二值检查单），一份里的几组仍分组作答，强制输出「每个条目 命中／不命中」，命中行给段号、30 字以内的短语和 10 字以内的依据，一行一条、不写前言和总结，最多 5 个同时跑；扫描全部返回后才开始改。修改交给一个子 agent 按清单顺序串行改完：它自己写补丁文件、自己用 `node scripts/apply-edits.mjs` 一次落盘并自检（先校验后写，`find` 出现 0 次或多次就整批不写，由它自己扩到唯一再跑），只做精确替换、不整篇重写；同一段命中多条合成一项。主 agent 不代跑脚本、不搬补丁内容。扫描和复核子 agent 只拿 `SKILL.md` 第一节，不给整份。复核只拿给它的文本（主 agent 重新生成的编号副本，段号本版重新计）、第一节和 reference，不给命中清单和改动记录，用同一套二值检查单重扫：A＋E＋D＋F、C＋I 只给改动段落摘录（改动段落加前后各一段，段号由主 agent 标），B＋G、J＋H、O 第一轮给全文、第二轮不分组一律给摘录，第一轮 0 条命中且无改动波及的组不补扫；先一轮、只对报过命中和改动波及的分组补一轮。合并后命中不超过 5 条时不派修改和复核子 agent，主 agent 自己改完、对 diff 交付；0 条直接交付。编号副本和补丁落盘都需要 node 18 以上，没有 node 时退回手工数段和逐条精确替换。没有子 agent 工具时按同一顺序自己做。H.md 始终跟 J＋H 那一份一起给，用户明确说标题不动时才不给。不建目录；改前留一份原文副本做 diff 对账，交付时删掉。

默认交成稿，必要的说明可放在正文之外。作者要清单时，每条改动一行，依次写原句、改后句、条目号和改动的层；原句从原文逐字抄。用户明确要求“审阅”“逐条检查”时，正文检查点逐条给出判定，含“无”；文中有标题时，标题检查也逐条给出判定。详细步骤见 [SKILL.md](SKILL.md)。

## 改写示例

以下均为教学用输入，没有未展示的补充材料。

**产品介绍，缺少数据：**

> 原文：该方案稳定可靠、快速响应、易于维护。
>
> 改写：这套方案运行稳定、响应快，也方便维护。

没有补写上线时间、响应速度或维护成本。原文缺少证据，可以向作者索取，不能用润色补出数据。

**故障反馈，有不确定性：**

> 原文：该问题被社区多次报告，被认为可能与内存泄漏有关，但原因尚未确认。
>
> 改写：社区多次报告这个问题。它被认为可能与内存泄漏有关，但原因尚未确认。

保留“可能有关”和“尚未确认”，不把推测改成因果结论，也不把原因判断擅自归给社区。

**更新说明，有真实的三项功能：**

> 原文：这次更新彰显了团队对创新的追求。它新增导出、搜索和批量重命名。离线编辑计划在下一版推出，目前尚未完成测试。
>
> 改写：这次更新新增导出、搜索和批量重命名。离线编辑计划在下一版推出，目前尚未完成测试。

保留三个功能，不为避开三段式删除条目或补造条目；计划和测试状态保持原意。

**已经清楚的文字：**

> 原文：先保存文件，再关闭窗口。未保存的修改会丢失。
>
> 改写：先保存文件，再关闭窗口。未保存的修改会丢失。

不要求每次调用都产生修改。

## 编辑原则

约束优先级是：保留信息和确定程度，遵守用户范围与文体，匹配作者声音，再处理具体表达问题。模式命中不能覆盖这些要求。

- 不编造功能、数据、来源、人物身份或第一人称经历。
- 保留否定、条件、归因、范围、时间和完成状态；“可能”不变成“确定”，“计划”不变成“已经”。
- 三项列表、四字格、被动句、破折号和连接词按作用判断，不机械删除。
- 先确认交付形态：输入是提纲式文本（标题分节、表格或冒号列举）时，让用户三选一——保持提纲式文档、合成自然文档、保留提纲式 md 标题的自然文档；只说要成文、没说形态的，先问选哪一种。
- 随笔可以保留个性，学术和商务文本保留正式程度；不把所有文章改成同一种口语。
- 文件编辑默认保留代码、命令、路径、链接目标、YAML、数据、标题结构和锚点。改标题或结构需要检查引用。
- 标题：交付形态只决定标题留不留（1、3 保留标题结构，2 分节标题并进正文）；标题文字和正文一样按 H.md 判、该改就改，用户明确说标题不动时才排除。改标题前查目录、锚点和交叉引用。
- 过度截短、省略与口语化是独立可选修复，只用于技术和专业领域文本；开始检查前问一次是否处理，同意才改，不默认改。成串单字动词恢复成完整动词，截短的术语用文章原词，动作化和内部简称改成直接描述，省略的条件、对象或步骤按原文补回；项目术语保留，换完变模糊或丢信息就不换。见 [reference/optional.md](reference/optional.md)。
- 默认交成稿，必要的说明可放在正文之外；作者问起改了什么时再给清单，不附草稿或自评分。

## 模式目录

正文检查点（A–F 沿用 PR #39 的分类，G、I、J 组为本仓库新增）和标题检查（独立模块，不占正文检查点编号；标题文字默认在编辑范围内）的分组、条目和读取顺序，直接见模式目录 [reference/patterns.md](reference/patterns.md)；每条的条件、示例和保留边界在 `reference/` 下的分组文件里，一次读一个文件。这是编辑问题清单，用于发现表达问题，不用于判断作者身份。

## 验证

文本案例见 [tests/README.md](tests/README.md)，包含短文本案例、一个 Markdown 文件样例和只读的结构检查脚本。新增案例覆盖标题检查、「保留 md 标题的自然文档」形态、过度截短、省略与口语化的可选修复和 AI-ish 表达；较早的长文对照检查了数字、条件、归因、作者态度和文件结构。单次、有限样例不能代表所有模型和文体，字数下降或模型自评分也不能证明效果。
