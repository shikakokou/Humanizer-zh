## H. 标题检查

标题包括文档标题（Markdown 的 H1，或文件名、首行标题）和分节标题（H2–H6），也包括图注和表题的题名。T1–T6 检查标题有没有题文不符、空泛承诺、公式化修辞、信息缺失、层级混乱和格式错误，不看它像不像 AI 写的。

这六条不占 35 条正文检查点的编号，只在标题进入编辑范围时使用：用户要求检查、修改或拟标题；用户要求审阅整篇文档；或交付形态是「合成自然文档」，分节标题要拆掉。标题改动会影响锚点、目录和交叉引用，动手前先读「改标题的程序」。

判定顺序：先看题文是否相符（T1），再看标题有没有提供信息（T2–T4），最后看结构与格式（T5–T6）。结构与格式只在准备改标题时处理；只检查时也可以列，但要和内容问题分开。

### T1 题文不符

标题里的范围、程度、数字、结论和时间，正文要有依据。正文说“可能”，标题不能写“已确认”；标题写“三个方法”，正文就要有三个；标题写“完整”“全部”，正文不能只覆盖一部分；标题说的主题要和这一节正文对得上。

**改写前：** 标题「导出失败的原因找到了」；正文「导出失败可能与权限设置有关，目前尚未确认。」

**改写后：** 导出失败可能与权限有关

**改写前：** 标题「五个排查步骤」；正文只给了三个步骤。

**改写后：** 三个排查步骤

**保留：** 标题比正文短，只概括正文已有的结论；正文补充的细节不必都写进标题。

### T2 空泛承诺

“一文读懂”“深度解析”“全面指南”“终极指南”“保姆级”“必看”“干货”“揭秘”“从入门到精通”“99% 的人不知道”这类词不提供信息，只承诺阅读收益。正文没有兑现，或文体不需要时，换成正文里真正有的对象和判断。

**改写前：** 标题「一文读懂缓存策略」；正文比较了几种缓存策略的适用场景。

**改写后：** 缓存策略的适用场景

**改写前：** 标题「揭秘团队效率翻倍的底层逻辑」；正文讲团队把评审拆成了两步。

**改写后：** 团队把评审拆成了两步

**保留：** 正文确实覆盖了标题承诺的深度，且刊发场景需要这类词；作者固定的栏目名、系列名、书名和课程名。

### T3 公式化修辞

标题里的假对比、假范围、重复副标题和没有回答的问句，把结构撑大，不增加信息：

- 假对比：“不是……而是……”先立一个没人持有的看法，再推翻；正文没有这个对照时，直接说结论。
- 假范围：“从……到……”两端不在同一尺度，假装覆盖全貌。
- 重复副标题：主标题和副标题说的是同一件事，或副标题只是“特有的坑”“那些事”这类弱标注。
- 问句不答：标题提问，正文没有回答。

**改写前：** 标题「不是工具问题，而是流程问题」；正文只讲流程改动，没有讨论工具。

**改写后：** 问题出在流程上

**改写前：** 标题「幻觉放大：多 Agent 特有的坑」。

**改写后：** 多 Agent 下幻觉会互相放大

**改写前：** 标题「从入门到精通：Python 异步编程」；正文只讲 asyncio 的基础用法。

**改写后：** Python 异步编程入门

**改写前：** 标题「为什么缓存会失效？」；正文只列了三种失效场景，没有解释原因。

**改写后：** 缓存失效的三个场景

**保留：** 正文确实做了对照；范围两端属于同一尺度；问句在正文里有明确回答；副标题补充了主标题没有的信息。

### T4 标题没有信息

标题只有并列名词、主题词或“其他”“补充”“相关说明”这类空标题，读者看完不知道这一节讲什么；标题依赖上下文（“这里”“上面”“这样改”），离开正文就指不明白。改成有对象、有判断或有具体范围的标题。

**改写前：** 标题「数据、算法与系统」；正文说模型效果主要受数据质量影响，算法差距反而不大。

**改写后：** 数据质量比算法更影响模型效果

**改写前：** 标题「其他」；正文讲导出失败时检查权限和路径。

**改写后：** 导出失败时的权限和路径检查

**保留：** 术语表、API 文档、规范条目、附录和更新记录可以只写名词或固定栏目名；判断标准是读者能否知道这一节讲什么。

### T5 层级与编号

- 跳级：文件模式下 H1 下直接出现 H3，或没有 H1 就开始分节；粘贴的片段除外。
- 多个 H1，或 H1 与 front matter 的 `title` 不一致。
- 编号重复或错位：“## 一、”下面又用“### 1.”起标题；编号和实际顺序对不上。
- 同级标题粒度差太多：一节讲一个按钮，另一节讲整个系统。粒度指同一层级覆盖的深度和范围；主题不属于本节，按 T1 或文档范围处理，不算 T5。
- 只有一个子节的父标题，层级是为了凑出来的。
- 同一文档里两个标题文字相同，或分节标题只是把 H1 重说一遍。

**改写前：**

```markdown
# 导出说明

### 权限
```

**改写后：**

```markdown
# 导出说明

## 权限
```

**保留：** 模板、目录和规范要求的编号；操作步骤的 1./2./3.；模板允许多个 H1 时；粘贴的片段可以没有 H1，文件模式按仓库的标题层级处理；不合并或拆分章节，除非用户明确要求。

### T6 标题格式

标题特有的格式问题：末尾的句号、逗号和分号；`#` 后缺空格；全角半角混用；中英文之间多余或缺失的空格；英文大小写不符合目标格式。表情符号、箭头和分隔线按 §20 判断，标题检查不重复计一条。

**改写前：** `## 导出说明。`

**改写后：** `## 导出说明`

**改写前：** `##导出说明`（想写成标题）

**改写后：** `## 导出说明`

**保留：** 平台或项目要求 emoji 时；状态标记本身承载含义时（“✅ 已通过”“⚠️ 注意”），见 §20；英文标题按项目既有的标题大小写。

## 检查结果怎么给

用户只要求检查标题时，给一张表，一行一个标题；命中栏写条目号，同一标题命中多条时合并写，问题和建议也合并成一条：

| 位置 | 原标题 | 命中 | 问题 | 建议 |
|---|---|---|---|---|
| H1 | 一文读懂缓存策略 | T1、T2 | 标题说“缓存策略”，正文只讲缓存失效；“一文读懂”只承诺阅读收益 | 缓存失效的三种原因 |

没有命中的标题不列。用户要求逐条检查时，每个标题一行：命中的写条目号和建议，没命中的处理写“不动”并给一句理由。用户要求改标题时，直接交改后的文档；要求先看建议再改时，给表并等确认。

## 拟标题

文档没有标题、用户要求起一个时，从正文里找它真正回答的问题或结论，用一句能独立成立的话做标题；正文只有材料没有结论时，写“对象＋这件事”，例如“导出失败的权限检查”，不要用承诺词（T2）或假对比（T3）替正文补一个结论。给两三个备选，各自说明对应正文的哪一部分；不替作者选立场。

## 改标题的程序

1. **先定范围。** 用户只要求检查时，给表，不动文件；要求修改时，按 T1–T6 改，只有命中的标题才动；没要求时，标题保持原样。
2. **改之前查引用。** 文件里的 `](#…)` 链接、目录条目、front matter 的 `title:`，以及正文里的“见第 X 节”“见上文”。标题是链接文字时，链接目标不动。引用找不到或改法不唯一时，先问。
3. **不动结构。** 不合并、不拆分章节，不改标题层级和数量，除非用户明确要求。层级变了，目录、锚点和引用一起改。
4. **逐字保留。** 产品名、API 名、命令、文件名、代码标识、引文、系列名和作者固定说法。
5. **记一条。** 改过的标题按清单格式记：原题 → 改后题 → 条目号；作者问起时再给。
6. **回头复核。** 改完再读这一节正文：标题和内容是否仍然对得上？首句是不是只在复读新标题（§24）？标题里的数字、范围、确定性有没有越过正文？
